**Дата анализа:** 2026 (на основе текущего состояния репозитория)  
**Цель:** Выявить корневые причины низкого качества retrieval (релевантные чанки часто не находятся, несмотря на присутствие в индексе) и предложить **конкретный, реализуемый, приоритетный план** улучшений без нарушения критических правил AGENTS.md.

**Ключевые артефакты данных (прямо указывают на проблемы):**
- Имена источников в metadata: `CП 347.pdf_7ead05d6-... .pdf`, `_СП229.pdf_56df0f9e-...` — пользователю показывается мусор.

- Таблицы: текст вида `"Т а б л и ц а 4.1 – ... \nh , м\nd | Значения m , МН/м..."` (пробелы в словах, кривой парсинг). Целые большие таблицы — один чанк.
- Текст: "допуска- ется принимать", "жилищно- коммунального", "исследователь- ский", куча "СП .1325800.2017 2 Нормативные ссылки", "....." из оглавлений.
- Чанки: много front-matter (предисловия, полные списки ГОСТ в начале), мало "очищенных" содержательных фрагментов.
- Лог assistant: поиск часто даёт топ-скоры 0.80–0.89, но иногда 0.48–0.58 (ниже THRESH=0.6); много 400-ошибок Yandex LLM; query никогда не логируется; нет логов реально возвращённых clause/source.
- process_light.log отсутствует сейчас (возможно, перезаписан/удалён).

**Структура проекта подтверждена** (соответствует AGENTS.md, за исключением того, что PDF_DIR на диске — `pdf_files/`).

## 2. Главные причины, почему retrieval часто не находит релевантные документы (даже если они физически есть)

Приоритезировано по влиянию на проблему (из AGENTS.md). Каждая причина подтверждена кодом/данными.

### 2.1. Катастрофически плохая предобработка текста из PDF (самая высокоприоритетная причина)
- `extract_text_and_tables_from_pdf` (process_pdf_index.py:70-91): `page_text.replace('\n', ' ')` — полностью разрушает параграфы, списки, структуру. Всё в одну "простыню".
- Нет де-дефисации переносов строк (очень частая проблема в PDF норм): "допуска- ется", "требова- ния".
- Нет удаления повторяющихся колонтитулов/шапок ("СП NNN.13330.20XX", "Издание официальное", номера страниц) — они размывают embedding почти каждого чанка.
- Нет отсева front-matter (титульные, оглавления, предисловия, "Содержание" с ".....") — эти чанки индексируются наравне с полезным контентом и "засоряют" результаты.
- Таблицы извлекаются дефолтным `extract_tables()` без `table_settings` — отсюда "Т а б л и ц а", сломанные заголовки, потеря структуры ячеек. Таблицы критичны для норм (размеры, допуски, требования в табличной форме).
- clean_text (94-98) — только collapse whitespace + control chars. Никакой нормализации (единицы, аббревиатуры, "п." vs "пункт").

**Следствие:** Даже если релевантный фрагмент "есть", его текст зашумлён/разорван так, что cosine similarity с пользовательским вопросом низкий.

### 2.2. Сломанный / нестабильный чанкинг (вторая по важности)
- `chunk_text` (101-123):
  - Сплиттер `re.split(r'(?<=[.!?;])\s+(?=[А-ЯA-Z0-9\(\"\'])', text)` крайне хрупкий после flatten + PDF-артефактов. Часто не сплитит вообще.
  - Fallback `text.split()` (по словам) при <2 предложениях.
  - Оверлап `cur = cur[-max(0, overlap // 10):]` — примитив (overlap=10 → 1 "предложение").
  - Результат (из статистики):
    - Медиана ~187 слов (близко к 200), но **max 11 384 слов** (один чанк = почти целая глава/приложение).
    - 2.7% чанков >400 слов; есть 84k-символьные монстры.
    - Много мелких (<80-300 chars).
- Таблицы: всегда целиком (даже 50+ строк / 9k+ chars). Embedding "среднее" по всей таблице — теряется конкретная строка "при β=30° значение = 0.044".
- Нет привязки к структуре документа (заголовки разделов, "п. 5.2.1", "Приложение В").

**Следствие:** 
- Мега-чанки дают "размытый" вектор (среднее по 10 разным требованиям) → низкий score на конкретный вопрос.
- Контекст разрывается посреди пункта.
- Перекрытие почти отсутствует.

### 2.3. Отсутствие/плохое качество структурных метаданных (препятствует точному поиску и фильтрации)
- `extract_clause` (51-54): одна примитивная re, которая хватает первое попавшееся число/код. В 90%+ случаев бесполезна. Нет "п.", "пп.", "Прил. А п. 3".
- Нет извлечения чистого кода документа ("СП 20.13330.2016"), названия, раздела.
- `source` = сырое грязное имя файла из download_pdfs.py.
- Метаданные не позволяют легко фильтровать ("только этот СП", "только таблицы", "пункты 6.x").
- В assistant.py: `include_neighbors` добавляет ±1 по глобальному индексу metadata (а не внутри документа) → часто тянет чанки из чужого СП.

### 2.4. Наивный retrieval (только dense semantic search)
- `search` в assistant.py (54-82):
  - Только `model.encode(query)` + `IndexFlatIP` (cosine).
  - Нет **hybrid** (lexical/BM25) — критично для норм, где важны точные "п. 6.5", "не менее 0,9 м", "СП 52.13330.2016", цифры.
  - Жёсткий `THRESH = 0.6` (эмпирический, часто отсекает релевантное; в логах есть скоры 0.48–0.58).
  - Нет префильтрации по упомянутым в вопросе документам/пунктам.
  - Нет query analysis/expansion/rewriting.
  - Реранкинга нет вообще (ни cross-encoder, ни даже эвристического).
  - Возвращает "сырые" метаданные без скоров, без объяснения.
- Пользовательские вопросы часто сложные/конкретные ("какая минимальная ширина эвакуационного коридора в секции МКД по СП 1.13130?"), embedding query не совпадает по формулировке с текстом нормы ("ширина проходов в свету в жилых зданиях должна быть не менее...").

**Следствие (прямо из проблемы в AGENTS):** "Retrieval часто не находит релевантные чанки, хотя они физически есть в индексе."

### 2.5. Проблемы с таблицами и embeddings
- Таблицы (25% чанков) — важнейший источник точных цифр — обрабатываются хуже всего.
- Модель `sentence-transformers/paraphrase-multilingual-mpnet-base-v2` — общая paraphrase-модель 2021 года. Не заточена под retrieval (asymmetric query-passage), regulatory/технический язык. Лучше работают e5 / BGE на бенчмарках.
- Нет специальной сериализации таблиц для embedding.
- Нет префиксов (для e5-style: "query: ", "passage: ").

### 2.6. Второстепенные / инфраструктурные
- Дублирование EMBEDDING_MODEL в config и assistant.py (жёстко захардкожено).
- Логирование слабое (нет query, нет clause в результатах поиска).
- LLM prompt очень длинный + строгий формат → частые 400 от Yandex (хотя это больше generation, чем retrieval).
- Кэширование embeddings/metadata хрупкое (сравнение только по длине).
- Нет инструмента оценки качества retrieval (нельзя измерить "стало лучше").

**Общий вывод:** retrieval страдает в первую очередь от **качества входных данных для embedding** (грязный текст + плохие границы чанков) и **отсутствия "умного" поиска** (гибрид + структура + фильтры). Семантический поиск сам по себе не справляется с высокоточными нормативными запросами без этих усилителей.

## 3. Конкретный план улучшений (учитывая слабый ноутбук: CPU, мало RAM, batch=2)

**Жёсткие ограничения (из AGENTS.md — соблюдать строго):**
- Не удалять/переименовывать: data/, scripts/, core/, pdf_files/ (PDF_DIR).
- Сохранять CPU-совместимость (batch_size=2, DEVICE="cpu", лёгкие модели).
- Точность цифр, пунктов, ссылок — критично. Всегда сохранять source/clause/chunk_index.
- Базовая структура хранения: JSON + NPY + FAISS (IndexFlatIP + нормализация) — не менять.
- Можно добавлять поля в metadata.json (обратно-совместимо).
- Reindex = `python scripts/process_pdf_index.py` должна продолжать работать.

**Принципы плана:**
- Инкрементально (Фаза 1 → измерить → Фаза 2).
- Сначала фиксим "грязь на входе" (самый высокий ROI).
- Добавляем eval с самого начала.
- Минимальные новые зависимости (предпочтительно чистый Python или уже знакомые).
- Все изменения с type hints, логированием, комментариями.
- После каждой значимой фазы — reindex + ручная проверка 5–10 реальных запросов + eval.

### 3.1. Фаза 0 — Инфраструктура измерения (сделать сразу, низкий риск)
- Создать `scripts/eval_retrieval.py` (новый, не нарушает структуру).
  - 15–25 "golden" запросов (взять из реального опыта + типичные для норм: высоты, ширины, уклоны, огнестойкость, эвакуация, таблицы и т.д.).
  - Для каждого: ожидаемые `source` (или doc_code), `clause` (или подстроки), ключевые числа/термины.
  - Метрики: 
    - Recall@k (есть ли хотя бы один релевантный чанк в топ-k).
    - "Clause hit" / "Doc hit".
    - MRR.
    - Средний скор релевантных.
  - Функция `evaluate(assistant, queries)` печатает таблицу до/после.
- Улучшить логирование в assistant.py: логировать сам query, топ-результаты с clause/source/score/is_table.
- Добавить в config.py: `EVAL_QUERIES` или отдельный json с тестами.
- **Цель фазы:** иметь объективный способ говорить "улучшилось на X%".

### 3.2. Фаза 1 — Предобработка + Чанкинг + Метаданные (высочайший приоритет, делать первой)
**Файлы:** в первую очередь `scripts/process_pdf_index.py`, `core/config.py`.

**Конкретные изменения:**

1. **Фикс извлечения текста (extract_text_and_tables_from_pdf):**
   - Добавить `fix_hyphenation(text)`:
     ```python
     text = re.sub(r'(\w)[-\u00ad]\s*\n?\s*(\w)', r'\1\2', text)  # дефис + перенос
     text = re.sub(r'(\w)-\s+(\w)', r'\1\2', text)  # после flatten
     ```
   - Для таблиц — улучшенные settings (экспериментально):
     ```python
     tables = page.extract_tables(table_settings={
         "vertical_strategy": "text",   # или "lines" если есть линии
         "horizontal_strategy": "text",
         "snap_tolerance": 5,
         "text_tolerance": 3,
         "intersection_tolerance": 3,
     }) or []
     ```
   - Улучшить сборку page_text: можно оставить extract_text, но собирать с лучшим сохранением абзацев (использовать `page.extract_text()` + дополнительно visitor для lines при необходимости). Главное — не просто replace \n на space глобально; лучше `' '.join(line.strip() for line in txt.splitlines() if line.strip())` + отдельно фиксить дефисы.
   - Опционально: извлекать `page_number = page.page_number` для метаданных (полезно для отладки).

2. **Улучшенный clean + boilerplate removal:**
   - В рамках одного документа собирать "шапки" (первые 1–2 строки + последние строки 5–10 страниц) и вырезать похожие фрагменты из всех страниц (простой set или fuzzy).
   - Глобальный список стоп-фрагментов: "МИНИСТЕРСТВО СТРОИТЕЛЬСТВА...", "Издание официальное", "СВОД ПРАВИЛ", "Введен в действие с", ".....".
   - Вырезать оглавления: если чанк содержит много "....." или "Содержание" + много номеров страниц — пропускать или сильно понижать вес (добавить поле `is_toc: True`).

3. **Радикально улучшенный chunk_text (цель: 300–600 слов / ~1500–3000 chars, с хорошим overlap и строгим уважением границ предложений/пунктов):**
   - **Приоритет — структурный чанкинг по заголовкам пунктов/разделов/приложений** (самое важное улучшение для норм):
     - Искать заголовки пунктов: `r'(?m)^(\d{1,2}(?:\.\d{1,2}){0,3})\s+([А-ЯA-Z].{5,80}?)(?=\n|$|\d+\.\d+)'` или проще "5.1.1 ", "п. 6.4", "Приложение А", "Раздел 7".
     - При нахождении — начинать новый чанк с префиксом "Пункт X.Y.Z: Название. " + текст.
   - Затем sentence-aware группировка (улучшаем оригинальную идею кода, а не отказываемся от неё):
     - Улучшенный sentence split (более терпимый к PDF-артефактам и flatten):
       ```python
       sents = re.split(r'(?<=[.!?])\s+(?=[А-ЯA-Z0-9"\'\(\u00ab])', text)
       ```
     - **Всегда группируем только целые предложения** (никогда не режем внутри предложения). Накапливаем предложения, пока суммарная длина группы (в словах) не превысит target (~400).
     - **Почему word-target (а не "ровно 4 предложения" или чисто по кол-ву предложений)?**
       - В русских строительных нормах предложения крайне неравномерны: короткие ("См. п. 5.2.") и очень длинные (60–120+ слов — одно сложное требование с условиями).
       - Фиксированное число предложений даёт огромный разброс размера чанков (от 50 до 3000+ слов) → плохие эмбеддинги (вектор "среднее" по нескольким независимым требованиям или слишком пустой чанк).
       - Word/char бюджет обеспечивает более стабильную информационную плотность чанка, при этом мы **сохраняем атомарность на уровне предложения** — это эволюция оригинального подхода "по предложениям + fallback", а не уход от него.
     - Overlap: последние 1–2 полных предложения (~60–80 слов).
   - Для таблиц:
     - Если таблица маленькая (<12–15 строк) — один чанк + хороший clean (заголовок + " | " или лучше "Колонка1=значение1; ...").
     - Если большая — разбивать на группы по 6–10 строк, **повторяя заголовок таблицы** в каждом подчанке. Это критично для retrieval по конкретным значениям.
   - Добавить в каждый чанк поля:
     - `doc_code`: "СП 20.13330.2016"
     - `clean_source`: красивое имя ("СП 20.13330.2016 Здания жилые многоквартирные")
     - `clause`: улучшенный (см. ниже)
     - `section_title`: если удалось вытащить
     - `is_toc`, `page` и т.д.

4. **Сильно улучшить extract_clause + извлечение структуры:**
   - Несколько проходов re (ordered by specificity):
     - Полные "п.?\s*(\d+(?:\.\d+)+[а-яА-Я]?)"
     - "Приложение\s+[А-ЯЁ]"
     - "Раздел\s+\d+"
     - "Таблица\s+[\d.]+"
     - Брать самый "глубокий" / последний в чанке.
   - Параллельно извлекать doc_code из текста/имени файла (re `([СC]П|СНиП|ГОСТ|СанПиН)\s*[\d.]+`).

5. **Другие в processing:**
   - Улучшить кэш: добавить версию процессинга (например, хэш параметров чанкинга + модели) в metadata, чтобы не было silent mismatch.
   - Сохранять порядок чанков внутри документа (добавить `doc_chunk_index`).
   - После создания документов — можно сделать лёгкую дедупликацию точных дубликатов внутри одного source.

**Ожидаемый эффект Фазы 1:** Значительно чище текст → выше cosine для релевантных; правильные границы чанков → меньше "размытых" векторов; clause/doc_code → основа для Фазы 2.

### 3.3. Фаза 2 — Умный retrieval: hybrid + фильтры + лёгкий rerank (главное оружие против "не находит")
**Файлы:** `core/assistant.py` (рефакторить search), возможно вынести `core/retrieval.py`; обновить config.

**Конкретно:**

1. **Query understanding (лёгкая, без LLM):**
   - `extract_query_entities(query: str)` → dict с `mentioned_docs: List[str]`, `mentioned_clauses: List[str]`, `keywords: List[str]`, `wants_table: bool`.
   - Простые re: `r'(СП|СНиП|ГОСТ|СанПиН)\s*[\d.]+[а-яА-Я\-]*'`, `r'п\.?\s*\d[\d.]*'`, единицы (м, мм, %, кПа, ° и т.д.).

2. **Гибридный поиск (обязательно):**
   - Добавить зависимость `rank-bm25` (очень лёгкая, один .py файл по сути; или реализовать мини-BM25 за 30 строк).
   - На этапе индексации (или лениво) построить BM25 index по всем текстам (или per-doc).
   - В search:
     - Если есть mentioned_docs — фильтровать candidates только по ним (огромный выигрыш по точности и скорости!).
     - Получить top-N (например 80–120) по dense.
     - Посчитать BM25 scores на тех же.
     - Fusion: `final_score = 0.6 * cosine + 0.4 * bm25_norm` (или tunable alpha).
   - Это решает точные совпадения номеров и цифр.

3. **Улучшенный candidate selection + neighbors:**
   - THRESH сделать configurable (начать с 0.35–0.45) или "брать минимум 8–10 даже ниже".
   - Neighbors: только внутри того же `source` (для этого хранить в metadata списки chunk indices per doc, или во время поиска группировать).
   - Возвращать `List[Dict]` с полями `score`, `rank`, `retrieval_method` (dense/hybrid).

4. **Лёгкий reranking (CPU-friendly):**
   - Вариант A (рекомендую сначала): **эвристический без новой модели**:
     - Бонусы: +0.15 если clause совпадает с упомянутым, +0.1 если exact keyword match (нормализованный), -0.05 за слишком длинный чанк, +0.05 если is_table и запрос про числа.
     - Сортировать по hybrid + бонусы.
   - Вариант B (если время позволяет): маленький cross-encoder.
     - Модель: поискать "multilingual cross-encoder" small (например ms-marco-MiniLM-L-6-v2 multilingual variant или "DiTy/cross-encoder-russian-msmarco" если существует). Загружать только в assistant.
     - Реранкить только top-30–50 кандидатов.
     - На CPU: 30 пар ~ 1–4 сек (приемлемо для ассистента). Протестировать.
   - Не использовать тяжёлые (bge-reranker-large и т.п.).

5. **Другие улучшения в retrieval:**
   - Добавить поддержку `filter_metadata` (doc_code, is_table и т.д.).
   - В generate_answer: использовать топ 6–8 (а не все после neighbors), truncate умно (по важности, а не просто 800 chars), показывать score/метод в отладке.
   - Сделать `retrieve(query, top_k=15)` отдельно от генерации.

**Ожидаемый эффект:** Для конкретных вопросов (с номером СП или "п.") точность подскочит в разы. Для общих семантических — hybrid + rerank дадут лучшие 5–8 чанков в контекст LLM.

### 3.4. Фаза 3 — Embeddings (средний приоритет, после 1–2)
- В config: сделать `EMBEDDING_MODEL` легко сменяемым.
- Протестировать `intfloat/multilingual-e5-base` (или e5-small-v2 для скорости).
  - При encode:
    - Для документов (в process): `f"passage: {text}"`
    - Для запросов (в assistant): `f"query: {query}"`
  - Это даёт сильный lift на retrieval benchmarks без изменения архитектуры.
- Сравнить скорость encode на CPU (batch=2) и качество на eval.
- Если e5-base слишком медленный — остаться на текущем или MiniLM.
- BGE-M3 интересен (dense+sparse в одном), но может быть тяжелее — только если есть время на эксперимент и ONNX/оптимизации.

### 3.5. Фаза 4 — Полировка, LLM, удобство (низкий приоритет для retrieval, но важно для end-to-end)
- Починить/упростить prompt Yandex (короче, убрать избыточный формат если вызывает 400; использовать temperature 0.0–0.1, ограничить context 4–6 чанков).

## 4. Итоговые рекомендации и приоритеты

**Топ-3 изменений, которые дадут наибольший эффект на "retrieval часто не находит":**
1. **Фикс чанкинга + дефисы + boilerplate removal** (Фаза 1) — чище и более "атомарные" векторы.
2. **Structural chunking + отличный extract_clause + doc_code** — даёт возможность точной фильтрации и rerank бонусов.
3. **Hybrid search + query entity extraction + фильтрация по упомянутым СП** (Фаза 2) — решает проблему "конкретный вопрос про конкретный документ/пункт".

Reranking и смена модели — усилители, но без 1–2 будут работать на грязных данных.

**После реализации плана** retrieval должен:
- Значительно чаще возвращать чанк с нужным "п. X.Y" или таблицей в топ-5.
- Лучше понимать "цифровые" и "конкретные" вопросы.
- Сохранять полную трассируемость (всегда source + clause).

Это полностью соответствует целям AGENTS.md: "Значительно улучшить качество retrieval", "Улучшить чанкинг и предобработку текста/таблиц", "Сделать понимание вопросов пользователя более точным", при этом оставаясь лёгким CPU-friendly решением.
